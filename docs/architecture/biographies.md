# Биографии артистов

Подсистема биографий (`internal/artistbio`, `internal/proxy/artist_info.go`, `internal/ai/biography_*.go`) гарантирует, что музыкальные клиенты получают в `getArtistInfo2` проверенное русскоязычное описание артиста (или пустое поле вместо английского/непроверенного текста).

## Доставка через Subsonic `getArtistInfo2`

Прокси перехватывает `GET` и `POST` запросы к `/rest/getArtistInfo2` (и `.view`):

1. Проверяет локальную эффективную биографию (`Store.EffectiveBiography`, таймаут чтения `75ms`).
2. Если готовой биографии нет, а ответ Navidrome валиден — ставит задачу в `Coordinator.Request(ctx, artistID, false)` и ждёт её завершения до `BIO_FIRST_REQUEST_WAIT` (`25s` по умолчанию, допустимый диапазон `5s..30s`).
3. Итоговое решение при формировании ответа:
   - Если в `poisq.db` есть ручное описание или подтверждённая автоматическая биография — подставляет её в поле `biography` (JSON и XML переписываются строго и безопасно).
   - Если в `poisq.db` ничего нет, но Navidrome вернул русский текст (`DetectBiographyLanguage`: `QualityOK`, `ru`, уверенность `≥ 0.90`, доля русского `≥ 0.80`) — пропускает его без изменений.
   - В остальных случаях очищает поле `biography` (`""`), чтобы клиентам не уходил английский текст или разметка.

## Приоритет ручных правок

В таблице `artist_biographies` ручное описание (`manual_text`, `manual_source_url`) хранится отдельно от ссылки на автоматического кандидата (`automatic_candidate_id`).

- При сохранении через Studio ручной текст обязательно проходит `DetectBiographyLanguage` (`ru`, `QualityOK`, `Confidence ≥ 0.90`, `RussianShare ≥ 0.80`).
- Пока задан `manual_text`, `EffectiveBiography` всегда возвращает его с флагом `Manual: true`, даже если фоновый пайплайн пересобирает автоматическую версию.
- Глобальный сброс кэша биографий в Studio очищает автоматических кандидатов, кэш веб-поиска и задачи, но **сохраняет все ручные описания**.

## Координация и жизненный цикл

`Coordinator` (`internal/artistbio/coordinator.go`) работает в один последовательный воркер (очередь на 100 артистов, пауза `20s` между стартами, таймаут задачи `150s`, до 2 ретраев с паузой `15s`). При старте сервиса `RecoverStaleJobs` переводит прерванные `queued`/`running` задачи в `retryable`.

Конечный автомат задачи (`artist_bio_jobs`):
- `queued` / `retryable` → `running` → `ready` | `no_data` | `retryable`.
- Живой прогресс по 9 стадиям (`identity`, `catalog`, `source_validation`, `evidence`, `web_discovery`, `summary_edit`, `summary_rewrite`, `summary_verify`, `summary_store`) отображается в реальном времени в Studio.

## Этапы сборки биографии (`SynthesisPipeline`)

### 1. Идентификация артиста (`identity.go`, `resolver.go`)

Чтобы не перепутать тёзок, личность артиста сопоставляется с локальной медиатекой (`TrackRepository.ArtistIdentityContext`: альбомы, треки, годы — причём чужие альбомы, где артист указан только гостем, исключаются).

- Кандидаты запрашиваются из **MusicBrainz** (до 8 артистов + релиз-группы и записи), с fallback на **Яндекс Музыку**, если MusicBrainz не дал подтверждённого совпадения.
- Детерминированный скоринг учитывает совпадение MBID (`1.0`), ISRC (`0.99`), эквивалентность имени/транслита (`+0.45`), пересечение альбомов и треков (`≥ 2` совпадений дают `0.96`). Порог автоподтверждения — **`0.95`**.
- В спорных случаях (`Confidence ≥ 0.60`, без противоречий и с обязательным пересечением по альбому/треку — кандидаты «только по имени» до LLM не допускаются) подключается `LLMArtistJudge.ArbitrateIdentity`.
- Подтверждённая личность кэшируется в `artist_bio_identity` на **30 дней**.

### 2. Сбор из 7 каталожных источников (`ingestion.go`, `source_*.go`)

Для подтверждённого артиста (до 4 источников параллельно на артиста, глобальный лимит 8) предварительно запрашиваются точные внешние ссылки из MusicBrainz (`LookupArtistLinks`: Wikidata, Wikipedia, Deezer, Apple Music, Discogs, Яндекс Музыка), после чего опрашиваются 7 источников:

1. **Wikipedia / Wikidata** (`source_exact.go`) — только по точным связям (`WikipediaURL`, `WikidataID`, свойство `P434 == mbid` или точное совпадение заголовка `ru.wikipedia.org` с упоминанием локального альбома/треков). Полный текст обрезается до `8 КБ` с отсечением разделов «Дискография», «Примечания», «Ссылки».
2. **Яндекс Музыка** (`source_yandex.go`) — `/artists/<id>/brief-info` (сначала без ключа, при `401/403` с OAuth-ключом `yandex`).
3. **Deezer** (`source_deezer.go`) — API-сверка альбомов + парсинг блока описания со страницы `/ru/artist/<id>`.
4. **Apple Music** (`source_catalogs.go`) — каталог `ru`, `editorialNotes` (требует ключ `apple_music`).
5. **Discogs** (`source_catalogs.go`) — профиль с очисткой BB-тегов (требует ключ `discogs`).
6. **TheAudioDB** (`source_exact.go`) — поиск по MBID (`strBiographyRU`, fallback `strBiographyEN`).
7. **Last.fm** (`source_exact.go`) — `artist.getinfo` по MBID с очисткой HTML и футеров (требует ключ `lastfm`).

### 3. Языковая проверка и валидированный перевод (`language.go`, `validation.go`)

`DetectBiographyLanguage` детерминированно отсекает короткие тексты (`< 80` букв), опасную разметку, избыток ссылок и повторы, а затем определяет язык (`ru`, `uk`, `be`, `en`, `de`, `fr`, `es`, `it`, `pl`, `mixed`, `und`).

- Русский текст (`Confidence ≥ 0.90`, `RussianShare ≥ 0.80`) сразу получает статус `accepted`.
- Иностранный текст переводится сегментами через `BiographyAI.Translate` с жёсткой проверкой сохранения защищённых сущностей (URL, чисел, дат, кавычек) и проходит независимую проверку точности перевода (`VerifyGrounding`, порог `≥ 0.95` и код `meaning:preserved`).

### 4. Веб-поиск Tavily (`web_search.go`)

Если каталожные источники не набрали достаточного объёма (`< 2` независимых провайдеров или `< 1200` рун текста), а также в режиме fallback при неразрешённом артисте с локальными альбомами, подключается **Tavily Search** (требует ключ `tavily`).

- Выполняется каскад запросов (`basic`, релизный уточняющий запрос, `advanced` при нехватке источников).
- Блокируются низкокачественные домены (соцсети, форумы, сайты текстов/билетов), зеркала Википедии сводятся в один origin `wikipedia`, URL проверяются на SSRF.
- Результаты кэшируются в `artist_bio_web_cache` (90 дней для непустых, 30 дней для пустых).

### 5. Трёхэтапный ИИ-синтез (`biography_synthesis.go`, `artist_grammar_profile.go`)

При наличии минимум **2 независимых источников** запускается синтез строго в JSON-режиме (предпочтительная модель Groq `openai/gpt-oss-120b` с fallback):

1. **`Collect`** — извлекает до 6 фактологических карточек из веб-сниппетов, детерминированно отбрасывая карточки с выдуманными числами/годами.
2. **`Edit`** — собирает связную русскую биографию (`150..1200` рун, `1..12` предложений). Перед генерацией `InferArtistGrammarProfile` детерминированно определяет число и род артиста (`solo male/female`, `duo`, `group`), чтобы исключить ошибки согласования; после генерации проверяются доля кириллицы, отсутствие английских дат/единиц, сохранение оригинального латинского имени и подтверждённость всех чисел.
3. **`Verify`** — проверяет каждое предложение против исходных фрагментов (`grounded`, уверенность `≥ 0.90`). При сбое запускается 2-я попытка с фидбэком верификатора, а в крайнем случае — фильтрация только подтверждённых предложений (`FilterGroundedSummary`).

К готовому саммари автоматически добавляется подпись:
`Саммари создано ИИ на основе проверенных источников: <список>.`

Если синтез не удался (например, нашёлся только 1 источник), выбирается лучший `accepted`-кандидат из каталогов по рангу (`ai_summary` > `official` > `yandex_music` > `wikipedia` > `apple_music` > `deezer` > `theaudiodb` > `lastfm` > `discogs`, оригинальный русский приоритетнее перевода).
